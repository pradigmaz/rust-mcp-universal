# Локальный Memory / Project Memory MCP на Rust

Этот файл нужен как рабочая выжимка: что стоит взять из `RMU` и из уже существующих memory / Obsidian MCP-серверов, чтобы собрать свой локальный `MCP` без внешних API, облака и чужой инфраструктуры.

Важно:

- это отдельный будущий контур, не часть текущего scope `RMU`;
- сюда можно складировать наработки и идеи, которые появились при развитии `RMU`, если потом они пригодятся для отдельного `memory / Obsidian MCP`;
- то есть этот файл - не roadmap текущего движка, а design-notes накопитель для следующего проекта.

Речь не про "ещё один сервер для заметок". Речь про локальную память проекта, с которой агент может работать как с нормальной рабочей средой:

- помнить архитектурные решения;
- держать связи между сущностями проекта;
- хранить прогресс, риски, договорённости и контекст;
- читать и обновлять это через `MCP`;
- при этом оставлять source of truth в понятных человеку Markdown-файлах, а не прятать всё в чёрный ящик.

## Что это за система

Это локальная project memory system для человека и агента.

Не просто:

- папка с заметками;
- chat memory;
- ещё один MCP "чтобы читать markdown";
- база знаний общего назначения обо всём подряд.

А именно слой долговременной памяти проекта, который:

- хранит архитектурные решения;
- фиксирует риски, ограничения, контекст и договорённости;
- связывает сущности проекта между собой;
- помогает агенту быстро входить в проект и не терять накопленное понимание;
- остаётся прозрачным для человека, потому что source of truth лежит в обычных Markdown-файлах.

Проще говоря, это попытка сделать для проекта нормальную рабочую память, а не надеяться, что агент каждый раз заново "додумается" до уже известных решений.

## Для чего она нужна

Такая система нужна, чтобы закрыть типовые провалы контекста, которые постоянно возникают в длинной работе:

- агент забывает, какие решения уже были приняты;
- повторно предлагает то, что уже отвергали;
- не видит связи между задачами, рисками и архитектурой;
- не понимает, что сейчас считается актуальным;
- теряет прогресс между сессиями;
- заставляет человека снова и снова восстанавливать контекст вручную.

Практическая цель системы:

- сократить стоимость повторного входа в проект;
- сделать агентную работу накопительной, а не одноразовой;
- отделить "истину о проекте" от эфемерного контекста чата;
- позволить человеку и агенту работать с одной и той же памятью;
- дать удобный интерфейс через `MCP`, не жертвуя читаемостью и переносимостью данных.

## Какие задачи она должна решать

В нормальном режиме такая система должна уметь:

- быстро объяснить, что это за проект и в каком он состоянии;
- показать ключевые решения и чем они мотивированы;
- найти связанные риски, ограничения и артефакты;
- открыть релевантные записи под конкретную задачу;
- обновить память после изменения проекта;
- помочь собрать стартовый context pack для новой сессии;
- не терять человека, если `MCP` временно не работает, потому что данные всё равно лежат в vault.

## Где границы системы

Это важно, чтобы система не расползлась в бесполезный комбайн.

Она не должна становиться:

- универсальной chat memory на все случаи жизни;
- свалкой всех диалогов подряд;
- тяжёлой облачной knowledge platform;
- opaque storage, который нельзя открыть руками;
- заменой обычной документации там, где нужна нормальная docs-страница.

Её фокус уже и полезнее:

- project memory;
- local-first;
- Obsidian / Markdown-friendly представление;
- agent-first retrieval и update через `MCP`;
- прозрачный operational lifecycle.

## Где здесь место для RAG

Если в `RMU` нужен в основном сильный `retrieval` по коду, то для `memory MCP` полноценный `RAG` уже уместен как first-class feature.

Потому что здесь вопросы другие:

- что мы уже решили;
- что сейчас считается актуальным;
- что агенту важно помнить перед изменением;
- что было раньше и чем это заменено;
- какие runbooks, risks и constraints относятся к теме.

То есть тут нужен не просто retrieval заметок, а knowledge retrieval + synthesis поверх:

- решений;
- архитектурных заметок;
- runbooks;
- glossary;
- progress / risk notes;
- Obsidian vault files.

Именно поэтому `memory MCP` логично делать местом, где живёт настоящий `RAG`, а `RMU` оставлять retrieval engine для кода.

## Что брать из `RMU`

Из `RMU` стоит брать не кодовый retrieval как таковой, а каркас вокруг него.

### 1. MCP-обвязку

Это уже хорошая база:

- protocol / initialize / tools-call;
- единый registry tools;
- ручное описание `inputSchema`;
- короткие и понятные `description` у tools и аргументов;
- единый формат ошибок и structured result.

Это полезно, потому что клиенты вроде `Kilo`, `Claude Desktop`, `Cursor` и другие очень быстро показывают, где сервер сделан аккуратно, а где "что-то работает, но пользоваться больно".

### 2. CLI + MCP поверх одного ядра

Это один из самых полезных паттернов в `RMU`.

Новый memory-сервер тоже лучше строить так:

- одно core-ядро;
- один CLI для ручной работы и отладки;
- один MCP server для агентов.

Такой подход сильно упрощает:

- отладку;
- тестирование;
- миграции;
- обслуживание базы;
- диагностику проблем в клиентах.

### 3. Preflight / compatibility / recovery

Это обязательно надо переносить как идею.

Для memory-MCP тоже нужен нормальный слой проверки:

- версия бинарника;
- версия схемы БД;
- совместимость индекса;
- stale process detection;
- безопасный recovery hint.

Без этого любой локальный сервер рано или поздно скатится в "почему оно вчера работало, а сегодня странно упало".

### 4. Privacy и safe output

Это тоже надо брать.

Даже если сервер локальный, он будет читать:

- названия проектов;
- внутренние заметки;
- персональные договорённости;
- ссылки на приватные репозитории;
- черновики архитектуры и задач.

Значит нужен слой, который умеет:

- маскировать чувствительные фрагменты;
- не светить лишние пути;
- аккуратно резать вывод наружу.

### 5. Maintenance и DB lifecycle

Из `RMU` полезно взять сам подход:

- `status`;
- `preflight`;
- `index_status`;
- `db_maintenance`;
- controlled rebuild.

Для memory-сервера это пригодится почти без изменений, только вместо "индекса кода" будет "индекс памяти проекта".

### 6. Context-pack / bootstrap подход

Из `RMU` надо брать не сами текущие retrieval-алгоритмы, а идею:

- не отдавать агенту сырые записи как попало;
- собирать стартовый context pack под задачу;
- давать краткий `brief`;
- иметь bootstrap payload для нового агента или новой сессии.

Для project memory это особенно важно: агенту редко нужен весь vault. Обычно ему нужен короткий, собранный, связанный кусок контекста.

## Что брать из внешних репозиториев

### Официальный `Memory MCP`

Брать:

- базовую модель `entity / relation / observation`;
- минимальный набор tools:
  - `create_entities`
  - `create_relations`
  - `add_observations`
  - `delete_entities`
  - `delete_relations`
  - `delete_observations`
  - `search_nodes`
  - `open_nodes`
  - `read_graph`

Почему это важно:

Это уже достаточно компактная и понятная модель памяти. Она не пытается сразу решать всё на свете и поэтому подходит как основа.

### `Context Portal (ConPort)`

Ссылка: `https://github.com/GreatScottyMac/context-portal`

Брать:

- саму идею `project-specific memory`, а не общей "болталочной" памяти;
- акцент на:
  - decisions
  - progress
  - architecture
  - glossary / specs
  - relationships между этими сущностями;
- `SQLite per workspace`;
- отдельное пространство памяти на каждый проект.

Почему это важно:

ConPort ближе всего к мысли "память именно о проекте, а не просто знания обо всём подряд".

### `Basic Memory`

Ссылка: `https://github.com/basicmachines-co/basic-memory`

Брать:

- local-first подход;
- Markdown как source of truth;
- SQLite как быстрый индекс поверх файлов;
- двустороннюю модель:
  - человек редактирует Markdown;
  - агент читает и пишет через MCP;
- knowledge graph, который строится поверх файлов, а не вместо файлов.

Почему это важно:

Это почти идеальный ориентир для "не хочу облако, не хочу внешний API, хочу локальную управляемую память, которую можно открыть обычным редактором".

### `obsidian-memory-mcp`

Ссылка: `https://github.com/YuNaga224/obsidian-memory-mcp`

Брать:

- хранение каждой сущности в отдельном `.md` файле;
- YAML frontmatter;
- `[[wikilinks]]` как связи;
- совместимость с Obsidian graph view;
- понятную структуру note-файла:
  - metadata
  - observations
  - relations

Почему это важно:

Это уже прямой мост к Obsidian-модели, а не просто generic memory storage.

### `Memento MCP`

Ссылка: `https://github.com/gannonh/memento-mcp`

Брать не стек, а идеи:

- temporal awareness;
- version history;
- fallback search;
- diagnostics по memory/index/search;
- уважение к связям и истории изменений.

Не брать как обязательную основу:

- `Neo4j` как базовый стор;
- внешний embedding API как обязательное условие работы.

Почему:

Для локального Rust-first v1 это лишнее утяжеление. Но сами идеи про историю, доверие к памяти и отладку очень хорошие.

## Что не надо брать в первую версию

### 1. Обязательные внешние API

Не надо строить базу на:

- OpenAI embeddings;
- облачном sync;
- SaaS-панели;
- внешней vector DB;
- OAuth-зависимостях.

Если потом это и добавлять, то только как optional слой.

### 2. Слишком тяжёлый backend

Для v1 не нужен обязательный:

- Neo4j;
- Qdrant;
- отдельный web backend;
- отдельный auth слой;
- server cluster.

Для локального инструмента это просто замедлит запуск и усложнит жизнь.

### 3. Чисто "чатовую память"

Новый сервер не должен превращаться в "склад фактов из переписок".

Нужна именно project memory:

- решения;
- договорённости;
- архитектура;
- ограничения;
- риски;
- TODO / progress;
- связи между ними.

Если туда тащить всё подряд из диалогов, память быстро превращается в мусор.

## Какая архитектура выглядит самой здравой

### Source of truth

Source of truth должен быть в Markdown-файлах внутри vault.

Причины:

- человек может открыть и понять данные без специального клиента;
- Git нормально хранит историю;
- Obsidian сразу работает с файлами;
- легко делать backup;
- не возникает ощущения, что память "заперта" внутри одной программы.

### Operational слой

Поверх Markdown нужен локальный `SQLite`.

Он нужен для:

- индекса;
- быстрого поиска;
- ссылок между сущностями;
- статусов синхронизации;
- derived metadata;
- быстрых выборок для MCP tools.

То есть:

- Markdown = source of truth;
- SQLite = рабочий индекс и derived state.

### Graph-модель

Базовые сущности для v1:

- `Project`
- `Module`
- `Decision`
- `ArchitectureNote`
- `Task`
- `ProgressEntry`
- `Risk`
- `Constraint`
- `GlossaryTerm`
- `Artifact`

Базовые связи:

- `relates_to`
- `depends_on`
- `supersedes`
- `documents`
- `blocks`
- `implements`
- `affects`
- `owned_by`
- `derived_from`

### File layout в vault

Один из разумных вариантов:

```text
vault/
  projects/
    <project-slug>/
      _index.md
      decisions/
      architecture/
      progress/
      risks/
      glossary/
      tasks/
      artifacts/
```

Каждая запись:

- отдельный Markdown-файл;
- frontmatter с типом, slug, timestamps, status;
- тело с кратким текстом;
- список наблюдений;
- ссылки на другие записи через `[[...]]`.

### MCP слой

Минимальный набор tools для v1:

- `set_project`
- `project_brief`
- `memory_status`
- `sync_vault`
- `search_memory`
- `open_nodes`
- `create_node`
- `update_node`
- `link_nodes`
- `unlink_nodes`
- `add_observation`
- `recent_changes`
- `decision_log`
- `risk_hotspots`

Для агента этого уже хватит, чтобы:

- войти в проект;
- быстро понять текущее состояние;
- находить нужный контекст;
- обновлять память без ручного блуждания по vault.

### CLI слой

Отдельный CLI тоже нужен сразу.

Минимум:

- `status`
- `sync`
- `brief`
- `search`
- `open`
- `doctor`
- `rebuild-index`

Это окупится сразу, потому что memory-система без CLI очень неудобна в обслуживании.

## Что стоит сделать в v1

### Шаг 1. База

Сделать локальный Rust core:

- vault scanner;
- Markdown parser;
- SQLite schema;
- sync engine;
- basic graph model.

### Шаг 2. MCP tools

Поднять минимальный `MCP`:

- search;
- open;
- create/update note;
- create relation;
- project brief;
- sync status.

### Шаг 3. Obsidian-friendly модель

Закрепить формат:

- frontmatter;
- wikilinks;
- стабильные slug/id;
- понятные sections в note-файлах.

### Шаг 4. Agent-first context

Добавить:

- bootstrap;
- context pack;
- recent changes;
- decision summary;
- unresolved risks.

Именно это превратит просто "хранилище заметок" в реальный инструмент для агента.

### Шаг 5. Diagnostics

Нужны:

- `preflight`;
- schema compatibility;
- rebuild hints;
- sync diagnostics;
- conflict reporting.

Без этого память начнёт тихо портиться, а пользователь узнает об этом слишком поздно.

## Что выглядит как лучший гибрид

Если собрать всё вместе, лучший вариант для своего проекта сейчас выглядит так:

- из `RMU` взять:
  - MCP server каркас
  - CLI + MCP поверх одного core
  - preflight / compatibility / maintenance
  - privacy
  - bootstrap / brief / context-pack подход
- из официального `Memory MCP` взять:
  - базовую модель `entity / relation / observation`
  - минимальный tool surface
- из `ConPort` взять:
  - ориентацию именно на project memory
  - decisions / progress / architecture / glossary как first-class сущности
  - workspace-local SQLite
- из `Basic Memory` взять:
  - local-first
  - Markdown как source of truth
  - SQLite как индекс поверх файлов
  - graph, который строится поверх vault
- из `obsidian-memory-mcp` взять:
  - отдельные `.md` файлы на сущности
  - frontmatter
  - `[[links]]`
  - совместимость с graph view Obsidian
- из `Memento` взять:
  - уважение к истории изменений
  - diagnostics
  - fallback-поведение при поиске

## Как относиться к `mempalace`

`mempalace` не выглядит как "готовая замена" для Obsidian-first project memory. Его правильнее рассматривать как возможный усилитель поверх собственного memory-контура, а не как новый source of truth.

Ключевая мысль:

- `mempalace` не должен становиться ещё одной отдельной памятью рядом с Obsidian vault;
- `mempalace` не должен становиться основным хранилищем вместо Markdown + SQLite;
- `mempalace` можно использовать как donor / enhancer для agent-facing слоя.

То есть не так:

- Obsidian memory;
- отдельно `mempalace`;
- отдельно ещё какой-то sync между ними.

Это почти гарантированно приведёт к:

- дублированию сущностей;
- drift между vault и memory-store;
- конфликтам при обновлении;
- неясному source of truth;
- лишней эксплуатационной сложности.

Правильнее так:

- Obsidian vault = source of truth;
- `SQLite` = индекс и derived state;
- собственный memory MCP = основной интерфейс для агента;
- идеи из `mempalace` = усиление retrieval / recall / context-assembly слоя.

### Где `mempalace` может реально усилить систему

Не как база хранения, а как набор идей и, возможно, отдельных адаптируемых компонентов:

- `wake-up` / session bootstrap перед началом новой агентной сессии;
- context compression;
- recall patterns для быстрого вытаскивания релевантного контекста;
- richer navigation по памяти;
- дополнительные эвристики сборки стартового пакета контекста;
- возможно, palace-метафора как optional view, если она реально помогает навигации.

Иными словами:

- наш blueprint отвечает на вопрос "где и как хранится правда";
- `mempalace` может помочь с вопросом "как агент быстро вспоминает и упаковывает эту правду под задачу".

### Где `mempalace` не должен управлять архитектурой

Для Obsidian-first memory-контурa не стоит подчинять архитектуру следующим assumptions:

- собственная memory-taxonomy как обязательный способ организации истины;
- отдельный primary store, живущий независимо от vault;
- модель "храним почти всё подряд из сессий и чатов";
- жёсткая зависимость от текущего внутреннего storage / pipeline `mempalace`.

Для project memory это хуже, чем подход:

- decisions / architecture / risks / constraints / progress как first-class сущности;
- Markdown-файлы как открываемый человеком источник;
- graph и индекс как производный слой поверх файлов;
- явный operational lifecycle (`status`, `doctor`, `preflight`, `rebuild-index`).

### Практический вывод

Если использовать `mempalace`, то не как:

- отдельную вторую память;
- замену Obsidian-first модели;
- причину ломать Markdown-first архитектуру.

А как:

- источник идей для agent UX;
- потенциальный слой wake-up / bootstrap / compression;
- временный экспериментальный retrieval enhancer;
- донор отдельных protocol-паттернов, если они переживут проверку практикой.

Коротко:

- `mempalace` = не "плюс ещё одна память";
- `mempalace` = не "новый хозяин архитектуры";
- `mempalace` = возможный enhancer для того memory MCP, который уже описан в этом документе.

## Итог

Если делать это нормально, то не нужен ни облачный memory backend, ни внешний API, ни тяжёлый графовый сервер.

Для сильного локального `Rust MCP` достаточно:

- Markdown vault;
- `SQLite`;
- нормальной graph-модели;
- хорошего sync слоя;
- agent-first tools;
- аккуратной обвязки вокруг совместимости, диагностики и обслуживания.

Тогда получится не просто "Obsidian bridge", а нормальная project memory system:

- понятная человеку;
- удобная агенту;
- локальная;
- расширяемая;
